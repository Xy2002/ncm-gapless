# 实现与验收记录

日期：2026-10-25 至 2026-10-26。目标客户端：网易云 3.1.42.205594 x64，CEF 91，Windows build 26200 x64。

## 已完成的接入

实现从纯音频核心推进到官方客户端播放流程：

```text
官方选曲与权限检查
    -> 接管受支持的播放加载
    -> 官方授权音源读取 / 必要时刷新失效链接
    -> MP3、FLAC、WAV 或经过时长验证的 AAC 解码
    -> 同一 AudioContext 提前调度当前与下一首
    -> 将加载、播放、进度、定位、结束事件反馈给官方界面
```

- `client-adapter.js`：按版本和接口能力发现官方 SDK、播放队列、状态枚举、预取与授权刷新入口。
- `aac-timing.js`：核对样本表、编码延迟、媒体/电影时基和有效范围，统一可确认的单音轨 AAC 时长元数据。音频数据保持原样。
- `gapless-engine.js`：共用音频时钟、预排下一首、取消、暂停、定位与代际失效处理。
- `netease-gapless.js`：接管受支持的加载，限制缓冲，管理预取与官方事件反馈；失败时恢复原始播放路径。
- PowerShell 启用、停用与状态脚本：自动发现现有回环端口与常用安装位置，无需修改安装文件。

## 实际遇到并修正的问题

1. 用户已删除旧补丁文件，但 0.1.6 仍驻留在现有页面内存。刷新页面后不再存在，干净基线的真实音源返回 200 并成功解码。
2. 应用层状态枚举的 `Playing` 为 2，原生播放事件中的播放值为 1，不能混用。适配器读取官方枚举。
3. 当前 SDK 的 `triggerRegisterCall` 将参数数组作为单一参数传入，不能按预期触发加载回执。适配器按原生逐参数形式分发，通过正反对照验证。
4. CEF 对生成 AAC 文件中的粗粒度编辑时长发生尾部截断，样本少 11～32 个采样。提升电影时基到媒体时基后恢复准确长度，与独立 FFmpeg 解码参考一致。
5. 网易云真实 AAC 的 `mdhd.duration` 与 `stts` 对编码延迟的计入方式不同。有效范围以样本时长表与编辑起点核对，并仅接受两者可解释一致的布局。
6. 重播旧曲目时旧地址再次返回 403。补丁复用官方用于刷新相同歌曲与音质的授权函数，明确跳过旧 RPC 缓存，每次失败读取最多刷新一次。没有将所有 403 一概认定为链接过期。
7. 官方 SDK 在定位调用的确认后才注册一次性定位监听器。定位回执延后到后续事件轮次，防止暂停时定位丢失回执。
8. 0.2.0 在第二首加载后接到官方再次下发的相同倍速，误走 `setRate -> seek -> play`，停止已经播放的音源并插入启动延迟。用户听到的开头卡顿由 WASAPI 回录复现：约 100.6 毫秒。相同倍速现在直接返回；实际修改倍速仍保留原逻辑。第二首播放中重设 1 倍速的离线渲染用例在修复前失败，修复后逐采样误差为 0；同一真实回录检查不再测得额外插入时间。
9. 0.2.2 将待下载 / 解码状态计入停用恢复判定，并根据最后一次暂停 / 播放请求恢复官方状态；加载中的 `play` 与 `pause` 使用同一状态，避免遗漏恢复请求。
10. 0.2.2 在覆盖 AAC 有效时长前检查原始精度依据。完整包布局只有在编辑时间单位达到一个源采样或更细，且最终范围符合整数采样等约束时才接受；有独立精确尾部的布局继续按原规则处理。粗粒度毫秒时长的整数转换不再充当精度证据。

## 0.2.2 回归验证

`node --test tests/controller.test.cjs tests/aac-timing.test.cjs` 的 27 个隔离用例在旧代码上为 18 失败 / 9 通过；修复后全部通过。控制流用例执行真实控制器和引擎，以可控 I/O、音频节点和虚拟时钟分别覆盖下载中与解码中的操作；AAC 用例使用不含音频包的生成元数据，并保留支持布局对照。

这类测试证明控制流与元数据判断，不是新的真实客户端停用或自然换歌试听验收。真实 CEF 的生成媒体解码与音频图渲染另行复测；具体结果见 `evidence/review-fixes-v0.2.2.json`。下表中的 0.2.1 自然回录与既有控制检查继续按原版本保留。

## 证据边界与剩余工作

离线渲染验证真实 CEF 的音频图输出；0.2.0 的自然播放记录仅验证真实曲目的预排、结束回调、官方状态交接与进度继续，未覆盖第二首开始后的声音中断，不能作为听感验收通过的依据。

0.2.1 新增默认输出设备的 WASAPI 回录对照：在内存中用真实解码参考波形定位前后音频，比较额外插入的时间。分析网格为 8 kHz（0.125 毫秒），相关度不足、回录溢出或插入时间超过 5 毫秒均不会判为通过。开发用诊断在退出时恢复临时引擎方法，不保存歌曲音频。具体结果见 `evidence/handoff-v0.2.1.json`。

首次自然回录虽然时移为 0，但未带限的采样率转换让部分匹配相关度不足，结果保留为未通过。测量工具改为两路在降采样前统一低通；生成信号的连续输出和人为插入 100 毫秒停顿两组对照确认检测能力，再重新从头播放 Dawn FM。后一次自然回录达到相关度门槛且无额外插入时间。

**尚未完成蓝牙链路或用户主观听感复验。** 当前回录仅证明本机默认输出设备与所测衔接；官方音效、媒体会话、客户端升级、复杂队列操作及其他 Windows/CPU 组合仍需单独验证。

本轮交付当前客户端版本的实验补丁与 Windows 便携脚本。Windows 通用版仍需建立系统、架构、客户端版本的实机矩阵；未知客户端会拒绝启用。

证据不包含音源地址、账户信息、请求头值或实际歌曲音频。AAC 适配参考了 [Apple 的编码延迟与轨道结构说明](https://developer.apple.com/documentation/quicktime-file-format/using_track_structures_to_represent_encode_delay_explictly)，实际行为由本机生成样本、独立解码参考和官方音源元数据共同验证。

## 0.3.0 macOS 接入

2026-10-26 在 macOS `27.0.1 arm64`、网易云 `3.1.12.3444` 完成实验适配。应用包为 Intel / Apple Silicon 通用二进制；CDP 实际报告 Chromium `116.0.5845.190`，UA 中的 Chrome 120 不是实际内核版本。

Mac 主页面为 `orpheus://orpheus/app.html`，通过 `ncmChannelOSX` 通信。适配器拦截 SDK 与旧界面两套 `callAdapter`，使用各自原调用处理未接管的命令，停用时恢复原属性。Windows 保留对 `channel.call` 的拦截，AAC 与音频调度核心共用。

三个 `.command` 入口通过 Python 启动器发现应用包、验证版本、选择回环端口、启用、停用和查看状态。运行依赖只有已有的 `websocket-client`。应用签名严格检查通过，安装文件未修改。

真实 Mac CEF 的 8 项核心、16 项编解码、7 项引擎 / 事件检查通过。已完成授权 FLAC 播放、预取、暂停、恢复和暂停时定位；从头自然播放的一次交接，调度边界差为 0 采样、错误和回退为 0。停用重新收到原生进度，冷启动、端口冲突与重复启用均通过。

Mac 原生进度使用数字字符串，旧停用检查的 `Number.isFinite(position)` 会错误地丢弃这些事件。新增回归用例先复现失败，再修正数值读取并通过实机停用复测。音频调度引擎未因此改动。

Mac 恢复还存在异步顺序问题：命令确认不代表定位或暂停完成，官方 SDK 的定位监听又可能晚于原生回执注册。适配器现在把当前已加载的授权播放信息直接交回官方 SDK，预先订阅定位完成事件，再执行官方暂停动作并等待原生暂停完成；避免后台队列重播覆盖恢复后的状态。缺失或不同曲目的播放信息会拒绝恢复。实机分别验证了播放中停用的位置保持与继续推进，以及暂停时停用后界面保持暂停、原生累计播放时钟不再推进。

上述自然播放仅证明调度和官方状态交接。Mac 设备输出回录、主观听感、Intel 实机、系统媒体控制、蓝牙及官方音效仍未验收。脱敏数据见 [macOS 验证记录](evidence/macos-validation.json)，运行方式见 [macOS 使用说明](macos.md)。

## 0.4.0 macOS 持续启用

macOS 27 使用系统快捷指令的 App 启动触发器，执行 `macos_launcher.py on-open`。模板从本地 JSON 生成，通过 Apple 的 `shortcuts sign` 签署后导入；源文件需要 `.shortcut` 扩展名。导入后首次手动开启该自动化与全局脚本许可，后续复用。

启用状态与调用入口保存在用户的 `Library/Application Support/NcmGapless`。状态文件用临时文件原子替换，文件锁串行化启用、停用和状态查询。启动事件等待当前操作结束后复查启用令牌与补丁状态，已安装时不重复加载。停止时先撤销令牌和入口，取得锁后再次清理配置，再卸载内存补丁。

普通实例通过 `NSRunningApplication.terminate` 正常退出，再以回环调试参数打开。已有调试实例等待就绪并复用；不会因端口未就绪而反复重启，也不会强制结束进程。版本、主页面和本机端点检查保持生效。客户端关闭时的状态和停止命令不需要创建 Python 环境。

实机完成系统界面关闭后的自动加载、停止后普通启动不注入、关闭客户端时停止、重新启用与辅助进程退出检查。原厂签名严格验证通过，主程序哈希未变。音频控制器仅更新版本标记，本轮没有重做音频输出验收。[生命周期记录](evidence/macos-automation-v0.4.0.json)、[资源入口研究](macos-persistence-research.md)

`Start-NcmGapless.command` 调用 `setup` 初始化向导。首次等待系统导入并打开对应编辑器，由用户确认自动化和脚本许可；之后真正从普通入口重开客户端，只有新的同令牌调用记录和当前页面都确认安装成功，才报告 `setupVerified: true`。旧成功记录不能代替本次自检。每次初始化沿用本次启用返回的令牌，验证启动前释放文件锁，让系统触发的短脚本可以执行；失败后的重试需要用户确认，最多三次，取消或失败会回滚该令牌对应的会话，不覆盖更新的启用请求。

已有配置的真实初始化自检通过；全新导入、交互取消、Ctrl+C、旧记录拒绝和并发回滚使用可控替身验证，尚未在第二台 Mac 进行首装验收。[初始化记录](evidence/macos-setup-v0.4.0.json)
